
| 33 | ✅ | Debugging compiled code: the design, and a first policy | The planned first policy -- interpret the program's code while debugging, leave the library compiled -- could not fix the case the task named: a breakpoint in a procedure given to the compiled `map` is reached in a synchronous nested run, which cannot wait, so the program stopped only when `map` returned (R82). So while a program is being debugged -- a breakpoint set, a step in progress, or paused -- every procedure compiled over an interpreted closure runs as that closure: the libraries' prebuilt code and `compileEnvironment` now keep the closures, and `interpretCompiledOver` switches the pairs through their frames, in the program's global environment and its registry's libraries, and back when debugging ends. Every breakpoint fires, the library's included; the callback case pauses at each hit exactly as with the interpreted library; stepping, `:bt` and locals see interpreted code. Not reached: code compiled from its definition (`tryCompileDefinition`), whose breakpoints the REPL still warns about; compiled procedures held in data; a pause the program asks for itself inside a nested run before the switch. Design written into `compiler_design.md`. | R54, R82 |
